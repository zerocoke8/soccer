# 2.5D 경기 화면 · 스프라이트 시험 계획 (브랜치 `outgame-sprite`)

> 상태: 구현 계획 · 2026-10-05 · 브랜치 `outgame-sprite` (웹 시험판 https://zerocoke8.github.io/soccer/sprite/ — 저장 키 `soccer-sprite.`).
> 레슨판 (`outgame-lesson`, /lesson/) · 본편 (main) 은 바꾸지 않는다. 엔진 (`js/engine/*`) · 데이터 규칙 · 밸런스는 바꾸지 않는다 — 화면만.
> **[가정]** = 기획자가 아직 정하지 않은 값, **[구현 결정]** = 이 계획이 정한 세부. 둘 다 §8 에 모은다.

## 0. 기획자 결정 (2026-10-05)

1. **2D 레이어로 만드는 2.5D.** 배경은 3D 엔진이 아니다. 생성 그림 층 (하늘 · 관중석 띠 · 잔디 바닥 · 선수 스프라이트) 을 겹치고, 카메라는 확대 · 이동만 한다 (돌리지 않는다).
2. **카메라 각도 = C (위에서 약 30° 내려다보기).** 쿼터뷰 (대각선 경기장) 는 쓰지 않는다.
3. **스프라이트는 한 방향만 그린다 (1번 안).** 오른쪽을 보는 "거의 옆모습" (몸 약 75° 돌림) · 2.5등신 · 위에서 30°. 왼쪽은 좌우 반전. 뒷모습은 그리지 않는다 (해 보고 꼭 필요하면 대기 · 달리기만 나중에, 약 1.3배).
4. **카메라 = 공을 따라간다 (평소)** · **직접 결정할 때 (버튼을 고르는 동안) 더 확대** · 킥오프 · 골 뒤 · 포제션 시작에는 잠깐 풀코트.
5. **경기장 바닥도 생성 그림** (위에서 똑바로 본 잔디 그림을 화면에서 눕힌다). 규칙 구역과 맞아야 하는 흰 선 · 박스 · 원 · 구역 강조는 같은 바닥 위에 정확한 자리로 그린다 (분필선 느낌).
6. **스프라이트 크기는 240px 한 가지** (원본 높이 240, 화면 기준 선수 키 약 64 ~ 72px, 결정 확대 2배에서도 폰에서 거의 1:1). 400px 판은 만들지 않는다.
7. 동작 영상 (시댄스 2.5 / 클링 3.0 → 프레임 → 스프라이트 시트) 은 이 계획 다음 단계 — 지금은 한 장짜리 정지 스프라이트 (기준 그림) 로 화면 구조 · 카메라를 먼저 만든다.

## 3. 투영 (`js/ui/view25.js` — 순수 함수, 테스트한다)

- **판 (ground plane) 좌표**: 판 = 폭 `PL` × 깊이 `PD` (판 px). 경기장 (필드) = 판 안의 `FL × FD` 사각형, 둘레에 런오프 `RU` (길이 방향) · `RV` (깊이 방향). [구현 결정] 시작값 `FL = 1244` (= 지금 필드 폭), `FD = 980`, `RU = 70`, `RV = 60`.
  - 필드 % → 판 좌표: `u = RU + (y / 100) · FL` (y = 골 방향, 0 = home 골 = 왼쪽), `v = RV + (x / 100) · FD` (x = 0 이 먼 터치라인 = 화면 위).
- **호모그래피** `Hm` (3×3): 필드 사각형 네 귀퉁이 → 화면 (필드 영역 `W × H` px, 지금 1244×528) 의 대칭 사다리꼴.
  - 가까운 터치라인 (v = RV + FD): y = `nearY` (H − 6), x = 0 ~ W. 먼 터치라인 (v = RV): y = `farY` (약 34), x = `W·farInset` ~ `W·(1 − farInset)`, `farInset` 0.085 [구현 결정 — 위에서 30° 의 완만한 원근].
  - 4점 → 3×3 해법 (표준 DLT). 판 밖 (런오프) 도 같은 식으로 투영된다.
- `project(x, y)` → `{ sx, sy, s }`: 화면 px 와 그 자리의 크기 배율 `s` (= 그 깊이에서 u 방향 1 판 px 의 화면 길이 ÷ 가까운 터치라인에서의 같은 값).
- `project3(u, v, h)`: 판 위 높이 h (판 px) 의 점 — 화면 y 에서 `h · s · liftK` 를 뺀다 (세운 물체 · 공 높이 · 골대). [구현 결정] liftK = 0.92 (30° 에서 수직 길이가 거의 그대로 보이게).
- `unproject(sx, sy)` → 필드 % (역행렬) — `fromPx` 대신.
- `cssMatrix3d()` → `matrix3d(...)` 문자열: 판 div (PL × PD, `transform-origin: 0 0`) 에 걸면 화면에서 `project` 와 정확히 같은 자리에 판 픽셀이 놓인다 (z = 0 점은 (u, v, 0, 1) → (X, Y, Z, W), 화면 = (X/W, Y/W)). 테스트가 문자열을 파싱해 같은 점을 비교한다.

## 4. 화면 구조 (2.5D 모드, `js/ui/screens/match.js` · `css/match.css`)

```
.pitch (그대로: 1268×708, overflow hidden)
  .w-sky                    하늘 그라데이션 (카메라 밖, 이동량 30% 시차) — 2.5D 모드만
  .m-field (그대로 자리 · W×H)
    .w-cam                  ★ 카메라 층: transform = translate(...) scale(z), origin 0 0 — 아래 전부 이 안
      .w-strip              먼 쪽 배경 띠 (투영된 먼 터치라인 뒤에 세운다)
      .w-ground             판 div (PL × PD) + matrix3d — 잔디 그림 · .pitch-bg (구역 · 선 · 강조) 를 판 안에
      svg.w-goals           서 있는 골대 두 개 (project3)
      .tok-layer / .m-ball / svg.pitch-svg / svg.pitch-svg.top / .pop-layer   (지금 그대로, 좌표만 투영)
    .charge-veil · .goal-fx (카메라 밖 — 지금처럼 필드 전체)
```

- 모드 판단 한 곳: `store.js` 에 `D25` (주소 `?d25=1` / `?flat=1` · `SPRITE_SITE`) + 테스트용 바꾸기 함수. `match.js` 는 모드에 따라 `toPx` / `fromPx` / `dirPx` 를 고른다 (평면 모드 코드 경로는 한 줄도 바뀌지 않게 — 기존 테스트 그대로).
- **토큰 (2.5D)**: 앵커 = 발. `--ts` (깊이 배율) 로 크기. 구조: `.tok-ground` (발밑 그림자 · 역할 고리 = 납작한 타원: carrier 금 · defender 흰 · receiver 점선 · cover 점선) → `.tok-figure` (스프라이트 `img` 또는 얼굴 원 스탠디) → `.tok-bar` · `.tok-name` (발 아래) · `.tok-bubble` (머리 위). 상태 클래스 (`fallen` · `dive` · `header` · `steal` · `claim` …) 는 `.tok-figure` 에 걸리게 CSS 를 2.5D 판으로.
  - 크기: 스프라이트 키 `SPR_H = 72 · s` (가까운 터치라인 72px), 스탠디 얼굴 원 지름 `40 · s`.
  - 방향: `.face-l` 이면 그림만 `scaleX(-1)` (이름표 · 바는 뒤집지 않는다).
  - 겹침: `z-index = 100 + round(sy)` (차지 · 컷인 층은 지금처럼 위).
- **이름표 · 말풍선 자리 고르기**: `tokenRect` · `labelCands` · `bubbleCands` 를 2.5D 판으로 (세로로 긴 사각형: 발 기준 위로 키만큼). CSS `lbl-*` · `bub-*` 오프셋도 같은 식으로 (JS 상자 = CSS 자리).
- **배치 간격**: `computeLayout(view, { aspect, tokenSize })` 에 판 기준 값 `aspect = FD / FL`, `tokenSize = 46 / FD` [구현 결정] — 가까이 선 두 선수가 몸 폭만큼 떨어지게.
- **공**: 투영 · 크기 `s` 배, 발 앞 (공격 방향으로 `0.35 · 폭`). 높이 있는 이동 (크로스 · 롱패스 · `arcBall`) = 바닥 직선 위로 `sin(πt) · 90 · s` 만큼 뜬다 + 바닥 그림자. `curveCtrl` 의 2.5D 판 = 위로 뜨는 곡선 (화살표 · 자취도 같은 모양).
- **골대**: 두 기둥 (`v = 중앙 ± 골 폭/2`, 높이 `GH`) · 크로스바 · 뒤 그물 (얇은 선 격자) — 흰 선 SVG. 골문 쪽 (`goalPt`) 은 지금 규칙 그대로.
- 레슨 화면은 바꾸지 않는다 (`.lesson-screen` 은 평면 그대로 — 2.5D CSS 는 `.match-screen.d25` 아래로만).

## 5. 카메라 (D2)

- 상태 `{ cx, cy, z }` = 화면 (필드 영역 W×H) 가운데에 올 월드 점 (투영 후 px) · 배율. `.w-cam { transform: translate(W/2 − z·cx, H/2 − z·cy) scale(z) }`.
- 범위 고정: 보이는 창 (W/z × H/z) 이 월드 사각형 (투영된 판 + 위쪽 배경 띠) 밖으로 나가지 않게 cx · cy 를 자른다. z = 1 이면 언제나 전체.
- **목표 고르기** (순수 함수 `cameraTarget(state, layout, view)` — 테스트):
  | 상황 | z | 가운데 |
  |---|---|---|
  | 경기 시작 첫 비트 · 골 연출 · 킥오프 배치 · 경기 끝 · ⏭ | 1 | 전체 |
  | 평소 (공 따라가기) | `Zf` = 1.4 (4배속 1.2) | 공 + 공격 방향으로 앞쪽 8% 미리 보기 |
  | 직접 결정할 때 (`paused(view)` — 공격 · 수비 · GK 배급) | `Zd` = 2.0 | carrier · defender · (보이면) cover 수비 · 고른 받는 선수 의 사각형 가운데. 그 사각형 (+여백 · 머리 높이) 이 창에 안 들어가면 z 를 Zf 까지 낮춘다 |
  | 액션 중 (`actionPhase`) | 지금 z | 공이 갈 곳 (패스 받는 선수 · 드리블 도착 · 슛 골문) |
- **움직임**: `.w-cam` 의 CSS transition — 결정 확대 들어가기 0.35s · 액션 `--t-act` · 재배치 `--t-move` (토큰과 같은 이징). 줄인 움직임 (reduced motion) = 순간 이동. ⏭ = 전체로 순간.
- **글자 크기 유지**: 확대해도 이름표 · 말풍선 · 결과 팝 · 링크 글 · 화살표 끝 글자는 화면 크기 그대로 — `--cam-z` 로 `scale(1 / z)` (자리 고르기 상자도 ÷ z, 화면 밖 판정은 지금 창 (월드 좌표) 기준).
- 하늘 (`.w-sky`) 은 카메라 이동의 30% 만 따라간다 (시차).

| 움직임 | 결정 확대 · 토글 · 받는 선수 탭 · 자동/수동 전환 = 0.35초 (`DECIDE_MS`, 배속과 무관 — 멈춰 있는 동안), 액션 = `--t-act` (공 이징 cubic-bezier(.45, .05, .55, .95)), 재배치 = `--t-move` (토큰 이징 cubic-bezier(.25, .8, .3, 1)), 골 연출 · 경기 끝 = `--t-move` 로 전체 | `.pitch` 의 `--t-cam` · `--e-cam` 이 `.w-cam` · `.w-sky` · `--cam-z` 트랜지션을 함께 정한다 |
| 순간 | 화면 열기 · ⏭ · 오류 새로 그리기 (`refresh`) · 줄인 움직임 (모든 카메라 이동 `--t-cam` 0 + CSS media) | |

### 10.2 [구현 결정] 표 → 상황

- **줄 고르기 (`cameraPhase`, 위가 먼저)**: 경기 끝 (`view.finished` — ⏭ 뒤 포함) · 골 연출 → 전체 / 액션 중 → 지금 z 로 공이 갈 곳 / 사람이 고르는 중 (`!busy && paused(view)`) → 결정 틀 / 킥오프 배치 (`view.lastBeat.type === 'kickoff'` — 경기 시작 · 골 뒤) → 전체 / 그 밖 → 따라가기. 표의 "포제션 시작" 은 킥오프만 (역습 · GK 배급 시작은 따라가기 · 결정 틀 — 공 뺏김마다 풀코트면 너무 자주 멀어진다).
- **경기 시작 첫 비트 · 잠깐 풀코트**: 경기 화면을 연 배치가 킥오프이고 사람이 고를 차례면 `T.start` (1x 0.7초) 동안 전체를 보여 준 뒤 결정 확대 (`startHold`). 자동이면 킥오프 배치 = 전체 → 첫 비트 액션도 z 1 (전체) → 재배치에서 따라가기. 골 뒤 수동이면 재배치 (킥오프 배치 = 전체) → 결과 한 줄 0.95초 → 결정 확대. 킥오프가 아닌 자리에서 화면을 열면 (이어하기) 바로 그 자리의 목표 (순간).
- **액션 중의 "공이 갈 곳"**: `actionPhase` 에서 공을 옮기는 마지막 자리 (`placeBallAt` · `arcBall` 이 적는 `ballDest`) — 패스 받는 선수 · 드리블 도착 (`nextBall`) · 슛 골문 / 세이브 자리 · 끊긴 자리 · 배급 받는 선수 · 롱패스 낙하 지점.
- **결정 틀 (`decideBoxes` → `cameraTarget('decide')`)**: core = 공 가진 선수 · 듀얼 수비 (틀이 1.4 에서도 안 들어가면 가운데를 core 쪽으로 당겨 둘은 여백까지 창 안). 넣어야 하는 것 = 고른 받는 선수 — 사람 공격: 패스 · 크로스 각각의 고른 선수 (없으면 기본값), 사람 수비: 상대 예상 액션이 패스 · 크로스면 그 받는 선수, GK 배급: 짧게 · 길게 받는 선수 (carrier = GK, 수비 = 롱패스를 다투는 MF). **에이스의 외침 선수도 넣어야 하는 것** (계획 표에 없던 것 — 2배로 잘라 "줘!" 선수가 HUD 아래로 가면 점선 · 배지가 화면 밖을 가리키고, 그 선수를 탭해 받는 선수로 고를 수 없다. 대신 그런 장면은 약 1.5 배). 보이면 넣는 것 (opt) = 커버 수비 · 다른 받는 선수 후보 — 나머지로 정한 창에 그림 상자가 걸리면 틀을 넓힌다 (반쯤 잘린 후보가 남지 않게).
- **창 밖 선수의 글자**: 발이 지금 카메라 창 밖인 선수에게는 이름표 · 말풍선을 달지 않는다 (예상 받는 선수가 창 밖이면 창 가장자리에 이름만 걸리거나, 그림은 HUD 아래인데 이름만 떠 있었다).
- **로그 서랍 자리**: 2.5D 는 필드 절반이 아니라 화면 (카메라 창) 절반 — 공 + 앞쪽 15 의 땅 점이 창 오른쪽 절반이면 왼쪽.

### 10.3 [구현 결정] 글자 크기 유지

- `--cam-z` 를 `@property` (숫자) 로 등록하고 `.m-field` 에서 `.w-cam` 과 같은 길이 · 이징으로 트랜지션 → 1 / z 가 확대 중에도 카메라 배율의 정확한 역수 (Chrome 에서 잰 차이 0.000, 이름표 화면 높이 16px 그대로).
- 이름표 · 말풍선: CSS `scale: calc(1 / var(--cam-z))` + 가로 비낌은 `transform` 대신 `translate` 속성, 줄어드는 기준 (`transform-origin`) = 붙는 점 (`--lox` · `--loy` / `--box` · `--boy`). 붙는 자리 (발 아래 `--ny` · 머리 위 `--fh` + 3 · 옆 `--fhw` + 5 · 비낌 4px) 는 월드 px — 확대하면 그림과 함께 멀어지고, 글자 상자만 화면 크기 그대로.
- 결과 한 줄 · 연계 문구: inline `transform: translate(…) scale(calc(1 / var(--cam-z, 1)))` (원점 0 0). 외침 배지: SVG `g` 에 CSS transform (속성을 덮는다). 미리보기 글자: `font-size` · 테두리 ÷ z. 화살표 · 궤적 · 외침 점선 · ✕: `stroke-width` · 점선 간격 ÷ z (화살촉은 선 굵기 단위라 함께).
- 확대와 함께 커지는 것 (월드 물체): 체력 바 · 특성 아이콘 · 유스 칩 · 공 · 골대 · 바닥 구역 글자 · ✕ 크기 · 발밑 타원.
- 자리 고르기: 글자 상자 폭 · 높이 · 글자 간격 × i (= 1 / z), 화면 밖 판정 · 끌어들이기 = 지금 카메라 목표의 창 (`camBounds` — 월드 좌표). 평면 모드는 `camBounds` = { 0, W, 0, H, i 1 } 이라 예전과 같은 수 (평면 장면 38개 픽셀 비교 — 다른 곳은 외침 말풍선 들썩임 · 연출 중간 프레임뿐).

### 11.1 켜기

### 11.2 열쇠 — 같은 비트 = 같은 자리, 토글은 규칙 자리가 바뀐 선수만

- 해시 열쇠 = `J1 | 경기 seed | view.possession | view.lastBeat.seq | view.attackingSide`, 선수마다 `| side:id` (듀얼 둘은 `| pair:…` 하나). 해시 = `zones.hash32` 와 같은 식 (FNV-1a + murmur3 — `layout.js` 사본, layout 은 엔진 없이 import) → mulberry32 수열. `Math.random` · 엔진 rng 없음.
- `lastBeat.seq` = 엔진 이벤트 번호 — 비트마다 바뀌고 저장본에 있다. **비트가 바뀌면 (공격 성공 · 실패 → 다음 자리) 새 무작위 자리.**
- 열쇠만으로는 모자라다: 화면이 그리는 view 는 미리보기 변형 (`resolvePreview` — 자동 진행 중이면 확정할 수 없는 받는 선수 후보를 숨기고, 스킬 · 필살기 토글은 후보 · 기본 받는 선수 · 도착 구역을 바꾼다) 이라 같은 비트 안에서도 역할 (receiver ↔ support) 과 일부 선수의 **규칙 자리**가 바뀐다.
  - J1 첫 구현: 비낌 계획을 그 역할로 정해서, 규칙 자리가 같아도 자동 ↔ 수동 전환에 선수가 옮겼다 → J1 에서 계획 (받는 선수 후보 = 모든 변형 후보 합집합) 을 고정해 고침.
  - **J1 검증 차단 버그 (J2 에서 고침)**: 토글이 몇몇 받는 선수의 규칙 자리를 바꾸면 (스루 패스 `sk_through_pass` · extra line 필살기 — 16_skill_row_4 #12 · #24 · #35, 17 · 28 · 31_ult_dribble_extra · 36), **규칙 자리가 그대로인 선수 — 공 가진 선수 · 공 · 듀얼 수비 · 커버 — 까지 최대 4.7 (필드 %) 옮겼다.** 원인: J1 의 화살표 가림 판정 · 제자리 고정 (pins) · 듀얼 둘 범위 · 겹침 검사가 *그리는 변형의* 받는 선수 규칙 자리로 계산되어, 다른 화살표가 가려지고 다른 선수가 고정됐다.
- **J2 해법 — 그 비트의 모든 변형을 한꺼번에 푼다** (`playJitter` → `jitterSolve`): 기준 view (`jitter.ref` = 엔진 view, 같은 비트일 때만 — 포제션 · 공격 팀 · phase · seq 가 같을 때; 아니면 그리는 view) 로 화면이 그릴 수 있는 변형 전부를 만든다 (`previewViews` — 그대로 · 자동 진행 (`deciding: false`) · `receiverPreviewBySkill` · `receiversBySkill` · `outcomesBySkill` 의 열쇠마다 스킬 변형; 필살기 · 스킬 + 필살기도 그 열쇠 중 하나). 변형마다 규칙 자리 (`playRule`) 를 계산하고, **단위 = (선수, 규칙 자리)** 로 흔든다 — 모든 변형에서 같은 자리인 선수는 단위 하나, 토글로 자리가 바뀌는 선수는 자리마다 단위 하나. 겹침 · 관계 · 화살표는 한 변형에 함께 나오는 단위끼리 모두 지키게 고른다. 그리는 변형은 답을 고르기만 한다.
- 결과 (§11.6 테스트 · 브라우저 확인): **같은 비트 안에서 어떤 변형 · 토글 (스킬 · 필살기 · 자동 / 수동 · 받는 선수 탭 · 결정 확대 · 다시 그리기 · 이어하기) 에서도 규칙 자리가 그대로인 선수는 정확히 같은 자리.** 옮기는 것은 규칙 자리가 바뀐 선수뿐이다 — 스루 패스 · extra line 필살기면 도착 구역이 바뀐 받는 선수 후보 (16_skill_row_4 = p6 · p7). 그 후보의 새 규칙 자리 때문에 `placeAll` 이 옆으로 민 선수가 있으면 그 선수도 규칙 자리가 바뀐 것이라 함께 옮긴다 (실제 시나리오에서는 나오지 않았다). **겹침 때문에 밀려 옮기는 이웃은 없다** (모든 변형의 자리를 함께 피해서 고르므로). 토글을 끄면 정확히 제자리로. 간파 단독 사용 (비트 없음) 도 그대로.
- 미리보기 변형이 아닌 view (기본 받는 선수만 바꿔 만든 view 등 — 화면은 그리지 않는다) 는 그 view 를 변형으로 더해 푼다 (그때는 규칙 자리가 기준과 모두 같을 때만 같은 답). 끝난 경기 · GK 배급 대기는 미리보기가 자리를 바꾸지 않아 배치 하나로 푼다.

### 12.2 슛 자리 (`layout.shotTarget` — 순수, 해시)

`shotTarget({ gkX, gkY, goalSide, kind, key, depth })` → `{ x, y, lift, side }` (필드 % · 높이 = 골대 높이 비율 · 공이 가는 쪽).

| kind | 가로 | 세로 | 높이 |
|---|---|---|---|
| `goal` (골 · 헤더 · 승부차기 골) | **GK 가 서 있지 않은 쪽 가장자리** — GK x < 50 이면 가까운 기둥 쪽 58 ~ 60, 아니면 먼 기둥 쪽 40 ~ 42. GK 가 가운데 (\|x − 50\| < 0.5 — 승부차기) 면 해시로 쪽 | 골라인 + depth: 평면 −0.5 (예전 99.5 · 0.5), 2.5D +2.12 (그물 깊이 3.54 의 0.6 — 그물 안) | 낮은 구석 0.1 ~ 0.2 / 높은 구석 0.5 ~ 0.62 (해시 반반, 공 바닥 — 공 위 끝도 그물 지붕 · 크로스바 아래) |
| `save` (세이브 · 승부차기 실축) | **GK 옆 2.5 ~ 3.5** (쪽 = 해시, 골문 안 GK 면 기둥 안쪽 39 ~ 61 에 남게 뒤집는다, 골문 밖 GK — 평면 ④ — 는 골문 가운데 쪽) | GK 깊이 | 손: 낮은 0.2 ~ 0.3 / 높은 0.5 ~ 0.62 (2.5D 는 다이브 자세를 고르는 데만 — 공은 실제 손 자리로 §12.3) |

- 열쇠 = `K1 | 경기 seed | 포제션 | 마지막 비트 seq` (`screens/match.js shotKey`) — 결정 중 view 와 그 결정의 연출 (`prevView`) 이 같아 **미리보기와 연출이 같은 자리**. 해시 = `layout.hash32` → mulberry32, 늘 같은 차례로 네 값 (쪽 · 높이 · 자리 · 거리). `Math.random` · 엔진 rng 없음.
- [구현 결정] **슛 미리보기 화살표도 같은 규칙** (가운데가 아니라): 슛 카드의 화살표 끝 = 골라인 위 그 골 자리 (바닥 직선, 끝 글자 "골문"), 사람 수비 미리보기의 상대 슛 길 끝도 같다 (우리 GK 가 없는 쪽). 궤적 (연출 뒤 남는 점선) 도 같은 길.

### 12.3 연출 (`screens/match.js shotPhase`)

- **골**: GK 가 공 쪽으로 옆 걸음 (`SHOT25.fall` 3 까지 · 거리 × 0.45 — **못 미친다**) + **뒤로 젖힌 다이브** (`--dive-r` 55°, 부호 = 그림 방향 · 위 8px). 공은 GK 반대쪽 구석, 그물 안으로 (2.5D: 공 요소 = 바닥 그림자 직선, 공 글자 = 끝 높이까지 오르는 직선 + 혹 `bump` 14 · s — `shotBall25`, 궤적 `trailShot25` = 같은 2차 곡선 + 바닥 그림자 길). 골라인을 넘는 때 (길 비율 — 공은 같은 빠르기) 부터 공 겹침 = 앞 층 바로 뒤 (그물 안에 보인다 · GK 보다는 앞). 공은 그물 안 그 높이에 머물고, 재배치 때 땅으로 떨어지며 (0.45 · `--t-move`) 킥오프 자리로.
- **세이브**: GK 가 세이브 자리까지 옆으로 날아 (`place` — 액션 길이) **앞으로 (슛 온 쪽) 몸을 뻗는다** (`--dive-r` 낮은 공 62° · 높은 공 30°, `.dive` + `.catching` 1.08). 공은 **그 자세의 손** (발 기준 키 × 0.9 를 기울기만큼 돌린 점 — `handsAt`) 에서 멈춘다: 땅 점 = 손 바로 아래 GK 깊이, 공 글자 가운데 = 손. 세이브 공은 선수 위 (기본 겹침).
- 다이브는 공이 뜬 뒤 (액션 0.3 — 빠른 배속에서는 자세 트랜지션 0.25초가 공보다 늦지 않게 바로). 다이브 동안 머리 옆 아이콘 (특성 · 유스) 은 숨긴다 (기울지 않으므로).
- **헤더**: 공이 뛰어오른 머리 높이 (`.tok.header` 위 16 · 1.06배) 에서 출발.
- ③ 중거리 슛의 골: GK 는 위와 같이, 막으려던 필드 수비는 예전 다이브 그대로. 필드 수비의 블록 (턴오버) · ④ 박스 연결 (GK 가 길목으로 튀어나옴 · 🧤) 은 그대로.
- 평면: GK 자리는 예전 그대로이고, 같은 옆 걸음 + 다이브 (얼굴 원 기울기), 골 = GK 반대쪽 가장자리 (골라인 안쪽 0.5), 세이브 = 옆으로 간 GK 앞 (예전 0.92).
- 승부차기: 골 = 해시로 고른 쪽 구석 (예전 가운데 + 6), 실축 = GK 가 날아 손에.

### 13.2 화면 (요소 · 크기 · 발 · 방향)

- **요소 하나**: 동작 목록 · idle 시트를 받으면 그 선수의 `.tok-figure.spr` 에서 정지 `img` 를 떼고 (사본 없음) `.tok-figure.spr.anim > span.spr-anim` 하나를 단다 (`upgradeFigure`). 배경 = 지금 동작의 시트, 칸 크기 · 앵커 · 배경 크기 · 반전 기준은 JS inline (`spriteAnim.animBox`), 프레임 = CSS `animation: var(--spr-name) var(--spr-dur) steps(var(--spr-n), jump-none) 0s var(--spr-iter) normal both` 로 `background-position` 0% → 100% (칸 0 … n − 1 을 같은 길이씩). `--spr-name` 은 `spr-play-a` / `-b` 를 번갈아 (동작을 바꾸면 첫 칸부터), 같은 반복 동작은 다시 시작하지 않는다 (배속만 바뀌면 길이만).
- **크기**: s = 1 월드 px — 칸 = `w × h × k`, k = 72 / 240 = 0.3 (정지 스프라이트 키 72 ÷ 원본 240 — 시트의 첫 칸 키도 240). 깊이 배율은 지금처럼 `.tok-figure` 의 `scale(--ts)`.
- **발**: 앵커 (토큰 원점 = 발밑 타원 가운데) = 칸 안 (`ax`, `footY`) → `left = −ax · k`, `top = −footY · k`. 프레임 연속 사진 (§13.8) 에서 앵커 ↔ 발밑 타원 가운데 차이 ≤ 0.02px, 정지 → 대기 첫 칸 바꾸기 전후 같은 자리 크롭에서 발 자리 · 키가 같다 (대기 첫 칸 실루엣 키 245 = 정지 240 보다 약 2% — 영상 가운데에서 자른 반복이라 자세가 조금 다르다).
- **방향**: `.face-l` 이면 `transform: scaleX(-1)` (기준 = 앵커 — inline `transform-origin`, 0.14초). 배치의 방향 (공 가진 선수 = 공격 방향, 나머지 = 공 쪽) 그대로, **단 재배치로 가로 6px 넘게 달리는 동안은 가는 쪽을 본다** (공 쪽을 보며 뒷걸음질로 달리던 것을 고침 — 도착해 대기로 돌아가면 배치의 방향). 정지 스프라이트 · 스탠디는 예전처럼.
- **이름표 · 말풍선 자리 상자 · 결정 틀 상자 = 정지 스프라이트 치수 그대로** ([구현 결정] — 계획의 둘 중 "정지 상자"): 글자 자리는 결정 · 재배치 때 고르는데 그때 그림은 대기 (칸 상자 44.4 × 75 ≈ 정지 42.3 × 72) 다. 동작 칸 최대 상자 (태클 발 왼쪽 40 · 세리머니 위 82 — s = 1) 로 잡으면 모든 장면의 이름표 · 카메라 틀이 실루엔만 넓어지고 기존 자리 (테스트 · 장면) 가 바뀐다. 넓은 동작 (태클 · 킥) 은 액션 0.8초 동안만 옆 이름표에 걸칠 수 있다.
- **자세 CSS**: 그림이 자세를 보여 주는 동작에는 겹치지 않는다 — `.fallen` 의 90° 눕기는 넘어짐 그림일 때 끔 (`[data-act="fall"]` — 시트를 아직 못 받아 대기면 예전처럼 눕힌다), `.header` 의 뛰어오름 (위 16 · 1.06배) 은 움직이는 스프라이트면 늘 끔 (`.header` 는 골 연출까지 남아 세리머니가 16px 떠 보였다 — 프레임 사진에서 찾아 고침). 반투명 · 흑백 (`.fallen` · `.beaten`) · 💫 · 크기 맥박 (뺏기 · 받기 · 잡기) · 빛 (필살기 · 고른 선수 · 차지) 은 그대로. 슛을 막으려던 필드 수비의 다이브 (40° 기울기) 는 움직이는 스프라이트면 하지 않고 버티기 동작.
- 겹침 · 발밑 타원 · 체력 바 · 이름표 · 말풍선 · 차지 · 컷인 층은 그대로.

### 13.4 시간

- **반복** (idle · run · dribble): `count / fps` × 배속 계수 (1 / speed) — 1x 대기 0.75초 · 달리기 0.58초 · 드리블 1.08초 한 바퀴, 2x · 4x 는 1/2 · 1/4.
- **한 번 · 끝 자세** (킥 · 패스 · 헤더 · 태클 · 버티기 · 넘어짐): 그 동작을 보여 주는 단계 길이 = 액션 `--t-act` (T.act 800 × 배속 계수 — 12장을 1x 0.8초, 원래 12fps 1.0초보다 조금 빠르게), 세리머니 = 골 연출 T.goal 900 × 배속 계수. 한 번은 끝나면 대기로, 끝 자세 (넘어짐 · 세리머니) 는 마지막 칸에 머물러 다음 재배치에서 끝난다.
- **재배치 달리기** = `--t-move` (T.move 650 × 배속 계수) 동안, 그 뒤 대기.
- **⏭** = 순간 배치 → 모두 대기 (예약된 "대기로 돌아가기" 는 `seq` 로 무효 · `cancelTimers`). **줄인 움직임** = JS 가 늘 대기 + CSS `animation: none` 으로 대기 첫 칸 그대로 (idle 시트만 내려받는다). 필살기 차지 · 컷인 층은 그대로.

### 13.5 메모리 — 내려받기와 디코드

- **두 가지는 다르다**: 내려받은 시트 (WebP 1.45 MB) 는 브라우저 HTTP 캐시 (디스크) 에 있고, 메모리를 쓰는 것은 그릴 때 푼 비트맵 (RGBA — 실루엔 한 벌 22.7 MB) 과 GPU 층이다. 아이폰 사파리가 탭을 다시 연 것은 디코드 · 층 메모리였다 (필살기 차지 때 큰 3D 판을 필터용 비트맵으로 다시 그림 — css/match.css `.w-cam::after` 주석).
- **기획자 질문 "게임 시작할 때 전부 다운받으면 메모리에 도움이 될까?"** — 메모리에는 도움이 되지 않는다. 미리 받으면 처음 쓸 때 빈 칸 · 끊김이 없어질 뿐이고 (그래서 경기 화면을 열 때 받는다), 메모리는 무엇을 디코드해 두느냐로 정해진다. 오히려 미리 **디코드** (`img.decode()` · 캔버스에 그려 두기 — 컷인 그림의 `art.preloadArt` 방식) 하면 쓰지 않는 동작까지 메모리에 올라간다. 모든 캐릭터를 게임 시작에 받으면 네트워크 · 디스크만 늘고 (캐릭터당 약 1.5 MB) 메모리 이득은 없다.
- **A1 이 하는 것**: (1) 경기 화면을 열 때 (2.5D) 그 경기에 나온 선수 (양 팀 7명) 의 캐릭터 중 목록이 있는 것만 목록을 부르고 (`cache: 'no-cache'` — 작다), 시트를 `fetch` 로 **내려받기만** 한다 (본문을 끝까지 읽고 버린다 — HTTP 캐시에 남게, Image · 캔버스 · decode 없음). idle 먼저, 줄인 움직임이면 idle 만. (2) 디코드는 브라우저가 그 요소를 그릴 때 — 선수마다 지금 시트 한 장. 정지 `img` 는 뗀다. (3) 목록 · 시트 Promise 는 모듈 캐시 (경기를 다시 열어도 다시 받지 않는다 — 들고 있는 것은 성공 여부뿐).
- 확인 (puppeteer, GitHub Pages 처럼 `Cache-Control: max-age=600` 을 주는 스크래치 서버): 경기 중 CSS 배경으로 시트를 바꿀 때마다 `fromCache=true` (다시 받지 않는다). `tools/shot.mjs` 의 내장 서버는 `no-store` 라 거기서는 바꿀 때마다 다시 받는다 (검사 도구에서만).
- 이미 쓴 시트의 비트맵을 언제 버리는지는 브라우저 몫이다 (Chrome · WebKit 모두 버릴 수 있는 이미지 캐시). 한 경기에서 열 동작을 다 쓰면 최대 약 22.7 MB — 캐릭터가 늘면 그만큼 늘어난다 (§13.8).

### 13.6 다음 캐릭터 추가하는 법

1. 정지 스프라이트: `art/sprites/base/<id>.png` → `node tools/sprites.mjs --only <id>` (data/sprites.json 항목 · `img/sprites/<id>.webp`).
2. 동작 영상 (시댄스 2.5 — 동작마다 4초 · 480p, 기준 그림 = 그 정지 스프라이트의 원본): 반복 동작 (대기 · 달리기 · 드리블) 은 첫 = 끝 프레임. 프롬프트는 실루엔 것을 본뜬다 (`art/sprites/_trials/video/silluen/<동작>.txt` — 로컬, "공 없음 · 단색 배경 · 카메라 고정 · 오른쪽을 본 옆모습", 공을 그리지 않게 'ball' 이라는 낱말을 피한다 — 패스 · 헤더는 다시 만들었다).
   - 반복: `node tools/seedance.mjs --first <base.png> --last <base.png> --prompt idle.txt --out <dir>/idle.mp4`
   - 한 번 · 끝 자세: `node tools/seedance.mjs --first <base.png> --prompt kick.txt --out <dir>/kick.mp4`
3. 시트: `node tools/video2sprite.mjs <dir>/<동작>.mp4 <out>/<동작> --fps <fps> --trim <loop|once|hold> [--max 12]`
   - 반복: `--trim loop` (idle 은 `--fps 8`, run · dribble 은 12 — 한 바퀴만), 한 번: `--trim once --max 12`, 끝 자세 (넘어짐 · 세리머니): `--trim hold --max 12`. `<out>/<동작>_sheet.png` 로 확인.
4. 목록: `node tools/sprite_anim.mjs <id> --from <out> [--map pass=pass2,header=header2] [--source "설명"]` — 시트를 `img/sprites/anim/<id>.<동작>.webp` 로 복사하고 목록 항목 (mode = trim, fps · count · w · h · footX · footY) · `foot0X` · `v` 를 적고 `data/sprites.json` 의 `anim` 필드를 단다. 시트만 바꿨으면 `--from` 없이 다시 돌려 `v` · `foot0X` 를 고친다.
5. 확인: `sprite-lab.html` (지금은 실루엔 고정), `node tools/shot.mjs <out> --only d25`, 그 캐릭터가 나오는 2.5D 경기. idle 은 꼭 있어야 한다 (없으면 그 캐릭터는 정지 스프라이트). 다른 동작은 빠져도 된다 (대신 동작).
